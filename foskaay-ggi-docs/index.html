FOSKAAY GASLESS GAMES INFRASTRUCTURE (GGI)

Add gasless play to any on-chain game

Foskaay Gasless Games Infrastructure (GGI) lets a game open a session on-chain, do everything inside for free, and settle once. Players never pay gas and never see a wallet popup. The game pays a small fixed fee per session instead of a fee per action, so an on-chain game can be as cheap to run as a normal web2 backend.

Why use it

  • Players pay nothing. No gas, no top-ups, no "insufficient funds" on a phone.
  • No wallet popups during play. A session key signs every action silently.
  • Cheap by design. The fee is per session, never per move, so a busy game costs the same as a quiet one.
  • Any game type. A board game, an idle farm, a card game and a whole MMO are the same to the rail: participants, an opaque state, signed events, one settlement.
  • Nothing to run. There is no validator, no RPC node and no rollup to operate. You deploy nothing extra.
  • Provable results. Every action is signed, so a tampered action breaks the signature and a fake result cannot settle.
  • True costs, up front. Fees are charged on testnet too, so you see real mainnet economics before you commit.

How it works

Think of a session as a room. You open the room, everything inside is free, and you settle it once at the end. Only the open and the settle touch the chain.

StepWhat happensOn-chain?
OpenCreate the session: participants, an optional rules blob, a lifetime, and an optional committed random seed.Yes, one transaction
ActRecord a signed action. The payload is opaque; the rail never reads it. As many actions as you like.No, free
SettleClose the session, reveal any committed seed, and seal the final digest.Yes, one transaction
The result is tamper-evident. Every action carries a signature and a sequence number, all folded into one digest. Anyone can replay the action log and check it matches the sealed digest, so the outcome cannot be quietly changed after the fact.

Built to fit your game, never the other way round

GGI is deliberately unopinionated. It gives you primitives and makes no decision for your game. It does not care how many players you have, how your data is laid out, or how often you settle.

The core (everything you need to ship)
ContractWhat it does
SessionRegistryOpen and close a session; set who may act for each participant; register session keys with scope and expiry.
SessionStateAccept signed actions: an opaque payload, a sequence number and a running digest.
RandomnessCommit-reveal random seeds for the games that ask. One stream by default, or as many as your game needs.
FeeVaultCollect the per-session fee and send it to a destination you choose.
Optional patterns (use them, ignore them, or build your own)
  • Batched settlement. Fold many settlements into one Merkle root per window, for the cheapest tier. You choose the window on-chain: 10 games every 35 minutes, or 1,000 games every 24 hours, or anything in between. Flushing is permissionless (no admin, no server). The trade-off: a result becomes final when the window flushes, so use it only where that is acceptable to your players.
  • Managed accounts. One account per player with slots for every game and feature.
  • Verifiers. A per-game referee that settles a disagreement by replaying the actions.
  • House or relayer as a participant. For games with an AI or house opponent.
A developer who wants a separate account per player, per feature, and a commit on every turn can do exactly that here and pay a little more. That is your cost to optimise. Our job is to make the floor cheap, not to tell you how to build.

Quickstart

Integrating is three things: install a package, write a small adapter for your game, and call four functions. There is no fork and no contract to copy.

npm install @foskaay/ggi-sdk
  1. Install @foskaay/ggi-sdk (and @foskaay/ggi-contracts if your own contract calls the rail directly).
  2. Write a small adapter that turns your game's state into the opaque payload. This is the only game-specific code, and it lives in your game.
  3. Call four functions: open, act, settle, and (optionally) dispute.
// Pseudo-code: the shape of an integration const ggi = new GgiClient({ network: 'arc-testnet' }); // 1. open a session for this match (one transaction) const sessionId = await ggi.open({ participants: 2, ttlSecs: 3600, rulesHash: hashOf(myGameRules), seedCommit: optionalCommit, }); // 2. record actions during play: free, signed, no popup await ggi.act(sessionId, { seat: 0, sequence: 1, payload: myMove }); // 3. settle once at the end (one transaction) await ggi.settle(sessionId, { digest: myFinalDigest, seeds: [revealedSeed] });

Full API reference and the adapter example ship with the SDK README. This page is the overview; the package docs go deeper.

Fees

  • Players pay nothing. Always. The game pays a small fixed fee per session. There is no player-pay option anywhere in the rail: paying is not a mode a dev can switch on, so your players never hit the "top up your wallet first" wall that kills most web3 games.
  • Charged twice per session: once at open and once at settle. An abandoned session pays only the open fee.
  • Never per action. A thousand moves and one move cost the same, so heavy games are not punished.
  • Paid in USDC, a stablecoin, so the price does not swing with a volatile token.
  • Set by the operator, changeable with one call and never baked into your code: the SDK reads the current fee at runtime.

What you run

Nothing extra. There is no validator, no RPC node and no rollup to operate. You deploy your own game as usual and call the four core contracts. The rail handles the room; your game owns its economy.

Honest limits, so there are no surprises. Inside a session the state is signed, not a live parallel machine, so a third party cannot read your mid-session state the way they can read a public account. A relayer submits the settlement, and it is trusted for timing, never for truth (the signatures decide what is true). And the rail ships its own session reader so sessions and receipts are visible.

Get started

Four steps from zero to a gasless game. If you already have a game, only steps 3 and 4 are new work.

1. Install
npm install @foskaay/ggi-sdk viem

@foskaay/ggi-sdk is the client. Add @foskaay/ggi-contracts only if your own contract calls the rail directly.

2. Create a client
import { GgiClient } from '@foskaay/ggi-sdk'; const ggi = new GgiClient({ network: 'testnet', // 'testnet' | 'mainnet' walletClient, // a viem WalletClient that signs });
3. Write a small adapter (the only game-specific code)

Your adapter turns a move into an opaque payload. The rail never reads it, so any game fits.

function toPayload(move) { // anything serialisable, and stable for the same move return { from: move.from, to: move.to, die: move.die }; }
4. Wire the four calls
// OPEN once per session (one transaction) const { sessionId } = await ggi.open({ participants: 2, ttlSecs: 3600, seeds: [mySeed], // only if your game needs randomness }); // ACT during play: free, signed, no popup, no chain write let state = { sessionId, digest: ZERO_DIGEST, eventCount: 0 }; state = ggi.act(state, { seat: 0, sequence: 1, payload: toPayload(myMove) }).state; // SETTLE once at the end (one transaction) await ggi.settle(sessionId, { digest: state.digest, seeds: [mySeed] });
That is the whole integration. No fork, no contract to copy, no infrastructure to run. Your game keeps its own economy; the rail owns the room.

Demo 1, live: Idle Farm (the cost proof)

Why this one first. Idle games produce the most actions of any genre. If the rail can make an idle farm gasless and cheap, it can make almost anything work. This demo is the clearest answer to the question every dev asks: "what does it actually cost me?"

What the player doesWhat happens on-chain
Taps to plant, water, harvest, upgradeNothing. Every action is signed off-chain by a session key and folded into a digest.
Opens the gameOne transaction: open a session (you, the sponsor, pay it).
Collects a random crop bonusFree. The value comes from the seed sealed before play.
Finishes the runOne settlement: close, reveal the seed, seal the result, pay the session fee.
What the demo screen shows
  • A grid of plots that grow and are harvested, so it looks alive, not like a test page.
  • A live meter: actions this session: N, chain writes: 2, cost so far: $0.0000x. It proves heavy play is free.
  • A random bonus crop, so a visitor sees commit-reveal randomness working.
  • A button to open this exact session in the Explorer, so the trust claim is one tap away.
The exact rules (the build follows this, no deviation)
  • Session: 1 participant (single player), ttl 3600 seconds.
  • Randomness: 1 stream, committed at open with a seed, revealed at settle.
  • Actions: plant, water, harvest, upgrade, each folded into the digest with an increasing sequence number. Payload is the game's own; the rail never reads it.
  • Scoring: purely the game's own (coins earned). The rail does not score.
  • Settle: at the run's end or on demand, close + reveal + seal + one session fee.
  • Fee: read at runtime with the SDK; never hardcoded.
Two modes you can switch between in the demo

The same game is playable in both settlement modes, so you can compare real numbers on real sessions instead of trusting a claim:

ModeWhat happensBest for
Unbatched (default)Each session settles on its own: close, reveal, seal, one fee. The result is final immediately.Anything that needs an instant per-session result.
BatchedThe session's digest is submitted into a window; the window flushes (full or past deadline) into one Merkle root. Cheaper per game, final when the window flushes.Idle and casual where a short delay is fine.

Switch modes on the demo screen and the live cost meter changes with it. That is the whole point: the same game, two cost tiers, your choice.

Who pays, and how the demo pays

Players pay nothing. The sponsor (the game operator) pays the tiny gas and the per-session fee. In this demo the sponsor is a small serverless function that signs those two transactions on the player's behalf, so the player just taps and plays. It reads the sponsor key and the Arc RPC from the environment; the key never reaches the browser.

Standalone by design. The demo shares the deployment and the sponsor key with the host site for convenience, but it is its own project: it imports nothing from the host game platform and keeps no host state. When the infrastructure moves to its own repo, the demo moves with it unchanged.

Environment variables used: GFG_Arc_Gasless_Sponsor_Key and GFG_Arc_RPC (both already set on the deployment).

Honest scope of the demo: one player, one session, no accounts and no persistence beyond the session. It is a proof of the rail, not a finished game. Anything beyond this spec goes into a later demo, and this page is updated FIRST whenever the build and the spec need to diverge.

Use cases

If your game has lots of small actions, the per-session fee is where the saving shows up. These genres benefit most:

GenreWhy it fits
Idle and farmingConstant ticks and actions. A per-action fee would destroy the model; a per-session fee does not.
Board and turn gamesMany moves, one result. Settle once when the match ends.
Card gamesEach player draws from their own deck: declare one random stream per player.
Arcade and casualShort rounds, instant fun. Cheap enough to let anyone play.
PvP arenasFast repeated actions, one provable outcome per match.
MMO and strategyPersistent worlds with many players and constant state changes.
Simulations and trainingThousands of actions with a single settlement at the end.
Building for web2 players? That is the point. Your users keep the normal web2 flow (sign in and play, no wallet setup, no gas, no popups) while you still get on-chain transparency. Nothing about their experience changes; only the layer underneath does.

FAQ and fixes

Do my players need a wallet?

No. They sign in however you onboard them, and every action is signed silently by a session key. They never see a wallet popup and never hold gas.

Does every move cost something?

No. Nothing is written to the chain during play. Cost appears only at open and settle, so a thousand actions cost the same as one.

What if a session is abandoned?

Only the open fee is paid. The settle fee is charged only when a session actually settles.

Can a player tamper with the result?

No. Every action is signed and folded into one digest. Changing an action breaks the signature, and a fake result cannot settle.

Do I have to use your account layout?

No. Layout, cadence and accounts are entirely your choice. One account per player, one per feature, or one per match all work unchanged.

How do I read what happened?

Every session and its sealed digest is readable from the contracts using the SDK read helpers. A session reader UI is part of the roadmap so receipts are visible to everyone.

Something looks wrong. Where do I start?

First check the network you passed to the client matches the contract addresses on this page. Then confirm the contracts are deployed on that network (mainnet is not live yet). Most issues are a network mismatch. If it persists, open an issue on the repository or contact us from the Support page and we will look with you.
